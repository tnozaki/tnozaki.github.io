数値の基数ソートなら uint64_t で基数を 10 とした場合最大 19 回しか再帰しないのでこれでもいいんだけどね。
しかし文字列を基数ソートする場合は文字列の長さだけ再帰するわけで簡単にスタックオーバーフロー攻撃できてしまうのである。

現実的にどのくらいの長さの文字列食わせたらスタックオーバーフローになるかの検証は暇な人がやってどうぞ。

そもそも誰もこんな移植性のない API 使ってない上に、唯一の使用例と思われる派生コード
[usr.bin/sort/radix_sort.c](https://codeberg.org/tnozaki/netbsd/src/branch/master/usr.bin/sort/radix_sort.c)

知らん間に O 発祥の reallocarry(3) が POSIX:2024 に入ってて驚いた、つーか POSIX:2024 にもビックリである、俺の記憶にあるのって C11 とか POSIX:2008 が最後だもんな。

そんで sort(1) はなぜ libc の radixsort(3) を使わず改変コピーを持ってるのかというと radixsort(3) はヌル文字で終端された文字列の配列をソートする API なのだが、sort(1) はソートする文字列はヌル文字で終端されておらず RECHEADER という構造体でバッファと長さで管理してるからそのまま渡せないからである。
これは radixsort(3) の設計が安直過ぎて応用効かんゴミカスだからで qsort(3) のようにソート対象を不透明オブジェクトにする設計にすべきだったよね。

ただ不透明オブジェクトから基数取り出すたびに関数ポインタ叩くような設計になっちゃうから性能へのペナルティが非常に大きくなるのが厄介ではある。
似たような話は存在しない過去記事で `sys/rbtree.h` より `sys/tree.h` の方が性能良いって話でやったっけな。

やるとしたら邪悪マクロでテンプレートもどきにしてインライン化するんですかね、どっちみちバイナリ互換どころかソース互換すらない新規 API 作る羽目になるし。
ただ不透明オブジェクトにしたところで数値のソートなら基本 Last Significant Digit (LSD) を使うからあんま意味ねえという気もしないでもない。

そもそも sort(1) で基数ソート使ってしまうと LC_COLLATE に従ったソートの実装で地獄を見るはずなのだが N の sort(1) はそもそも国際化をバッサリ切り捨ててダメだった。
やっぱりシングルユーザーで起動したら終わりってな OS じゃユーザーランドなんて永遠に改善しないのである。

POSIX Locale Collation API 自体がやっつけのゴミカスで国際化された照合順序でソートしろとなると qsort(3) + strcoll(3) 程度しか考慮されてないのでクソの役にも立たないのが悪いのである。
ICU の場合 `icu::CollationKey::getByteArray()` という API 使うことで 8bit なバケツで基数ソートできるんだけど、これはこれで変換のコスト掛るしなぁ。

F の sort(1) の radixsort.c は完全に書き直されていて国際化対応もマルチスレッド対応もされてるのでとても偉い、ソース解読はやる気がまったく今湧いてこないので来世まで待ってくれ。

国際化について radixsort(3) は申し訳程度に照合順をテーブルで渡せるようにはなってるんだけど、しょせんシングルバイト圏でしか役に立たん時代遅れのシロモノなので無い方がマシですらある。

基数ソートってのは原理としてバケツソートの応用なので、文字列の場合は先頭から一文字つづバケツに放り込んでいくのだが、国際化が絡むとこの「一文字」ってやつが曲者で、マルチバイトの欠片であればそもそも正しいソート結果は望めない。
じゃあワイド文字に変換すると今度はバケツが 8bit から 32bit になってこれまた破綻必至、とても厄介なのだ。

似たような話がこちらも存在しない過去記事 nvi の ワイド文字対応 regex(3) がぶっ壊れてる件で文字列検索アルゴリズムの BM 法をワイド文字に適用するにはどうするかで出てきたような記憶ある。
あっちはスキップテーブルを配列にするのやめてリストにしても性能劣化はギリ許容範囲って結論だったんだっけ、もう覚えてねえ。

余談だけど文字列でなく数値を基数ソートするケース、ネットに転がってる情報処理の授業のテキストとそれをパクったいかがでしたか記事そしてさらにそれをパクった生成 AI のお出しする実装って決まって基数を 10 つまりバケツ 10 個にしたのばっかなんだよな。
これはちょっと3秒くらい考えればわかることだと思うんだけど(語録)、バケツはできるだけ大きくした方が性能出るから基数は 256 くらいにしておけ。
くれぐれも生成 AI のお出しするコードを鵜呑みにする認知的降伏者にだけはならないように、まぁもう手遅れかこの猫の国。
