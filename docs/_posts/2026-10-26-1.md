## Ghidra のインストール

[Ghidra](https://github.com/NationalSecurityAgency/ghidra)
は悪の枢軸トランプ帝政アメリカの国家安全保障局 (NSA) が公開してるリバースコンパイルツール。

NSA は高度な暗号技術輸出を禁止しようとしたり(合衆国憲法修正第 1 条を盾に RSA 暗号のソースを書籍にして海外に持ち出した)
かつてはインターネッツのバックボーンに
[641A 号室](https://en.wikipedia.org/wiki/Room_641A)
なる盗聴部屋を作ってたことで悪名高いアレ、あまり近寄りたくない存在である。
俺の処刑もインターネットで公開するんでしょ！エロ同人みたいに！エロ同人みたいに！

インストールはアーカイブを適当な場所に展開するだけ、ただし Java で実装されてるので JRE のインストールが必要。
あと一部のプラグインに Python が必要になるけど使わないなら入れなくてよい。

この令和の世でも Java アプリを起動するのに *.bat をダブルクリックして黒窓がポップアップするいう地獄。
仮想マシンつまり jvm.exe に引数として渡さなければいけない宿命のせいだが、せめて *.jar をダブルクリックしたら実行できるくらいにならんのか。
なお当の故 Sun Microsystem は俺達にはブラウザからの Applet 実行そして *.jnlp すなわち Java Web Start があるなどという意味不明の供述をしており…

昔は Unix なんかでも `execve` システムコールで直接 .class を実行できるパッチなんてあったんだけどね(カーネルが magic が Java class なら JVM を探し実行する)。
みんな Java を嫌っていたのでそんなパッチが accept される未来は無かった結果がこれ。

プロジェクトを作成して解析対象の実行ファイルや共有ライブラリをインポートする手順は割愛、難しくないのでマニュアル読んでどうぞ。

## まずは仮想関数テーブルを探す

COM の正体とはざっくりと言えば GUID と紐づけられた IUnknown インタフェースを実装するクラスの仮想関数テーブルでしかないので、まずはそれを探すことにする。
C++ ならコンパイル時に決定済だろうしどうせ書換禁止領域に配置されてんだろと考えて Ghidra で解析した疑似アセンブラコードから .text セクションを調べてみる。

そんで出てきたのがこれ。

```asm
                             PTR_FUN_02001384                                XREF[2]:     FUN_02002d93:02002d9c(*), 
                                                                                          FUN_02002e16:02002e2c(*)  
        02001384 68 5f 00 02     addr       FUN_02005f68
        02001388 c6 ae 00 02     addr       FUN_0200aec6
        0200138c ca 2d 00 02     addr       FUN_02002dca
        02001390 60 2e 00 02     addr       FUN_02002e60
…
```

`addr` つまりメモリアドレスの配列がずらずら続いてるのだけど、先頭と判定された位置に PTR_FUN_<先頭のアドレス> という名前でラベルを貼られている。

ここから同じようなのが十数個ならんでるのでここが MIDL が出力したサーバースタブコードっぽいですな。

このメモリアドレスは何を指すアドレスかというと、実行コードすなわち関数のアドレスである。
つまり仮想関数テーブルとはただの関数ポインタの配列ってことがよくわかる。

これらの関数も書換禁止領域に置かれていて実行コードの先頭に FUN_<先頭のアドレス> というラベルが貼られているので、クリックすすればジャンプできる。

```c
void FUN_02005f68(int param_1,undefined4 *param_2,undefined4 *param_3)

{
  FUN_020034cb(*(HANDLE *)(param_1 + 0x20),*(undefined4 *)(param_1 + 8),
               *(undefined4 *)(param_1 + 0xc),(int *)(param_1 + 0x10),param_2,param_3);
  return;
}
```

## コンストラクタを探せ

そんでこの仮想関数テーブルにはコンストラクタは出現しないのでその探し方である。

まず C++ のコンストラクタについてについてのおさらい。

```c++
#include <iostream>
class Greeting {
	const char* name;
	Greeting(const char* name) {
		this->name = name;
	}
	~Greeting() {
	}
	void Hello() {
		std::cout << "Hello " << this->name << "." << std::endl;
	}
};
int
main()
{
	auto greeting = new Greeting("Mike");
	if (greeting != nullptr) {
		greeting->Hello();
		delete greeting;
		greeting = nullptr;
	}
	return EXIT_SUCCESS;
}
```

このコードは C で書いたら以下のようなコードになる。

```c++
#include <stdio.h>
#include <stdlib.h>

#define operator_new	malloc
#define operator_delete	free

/* クラス */
struct GreetingVFTBL;
struct Greeting {
	/* メンバ関数 */
	const struct GreetingVFTBL* vftbl;
	/* メンバ変数 */
	const char* name;
};
/* 仮想関数テーブル */
struct GreetingVFTBL {
	void (*Hello)(struct Greeting*);
	void (*Delete)(struct Greeting*);
};
static void Greeting_Hello(struct Greeting*);
static void Greeting_Delete(struct Greeting*);
static const struct GreetingVFTBL Greeting_vftbl = {
	&Greeting_Hello,
	&Greeting_Delete
};
/* コンストラクタ */
void
Greeting_Greeting(struct Greeting* greeting, const char *name)
{
	greeting->vftbl = &Greeting_vftbl;
	greeting->name = name; 
}
/* メンバ関数の実装 */
static void
Greeting_Hello(struct Greeting* foo)
{
	fputs("Hello ", stdout);
	fputs(foo->name, stdout);
	puts(".");
}
/* デストラクタ */
static void
Greeting_Delete(struct Greeting* foo)
{
	operator_delete(foo);
}
int
main()
{
	struct Greeting* greeting;
	greeting = (struct Greeting*)operator_new(sizeof(*greeting));
	if (greeting != NULL) {
		Greeting_Greeting(greeting, "Mike");
		(*greeting->vftbl->Hello)(greeting);
		(*greeting->vftbl->Delete)(greeting);
		greeting = NULL;
	}
	return EXIT_SUCCESS;
}
```

やってることは

1. メモリアロケータによってヒープ上にインスタンス用のメモリ確保が成功するとインスタンスを引数にコンストラクタが呼ばれる
2. コンストラクタ内でメモリの先頭に仮想関数テーブルのポインタが格納される
3. メンバ関数とデストラクタはこの仮想関数テーブルのポインタ経由でこのインスタンスを第 1 引数に呼びだされる
4. デストラクタでメモリが解放される

なのだがポイントは 2. で

* 仮想関数テーブルを参照して
* 第 1 引数にそれを代入してる

コードがあればそれはコンストラクタの可能性が高いってことなんですわ。

それじゃさっそくこのラベルを参照してる関数を検索してみようか、仮想関数テーブルのラベル上で 右クリック -> Reference -> Show Reference to ラベル名を選んでみよか。

その結果 `FUN_02002e16` がヒットした。

![ヒットした参照先の一覧画面](/assets/images/2026-10-26-1/2.png)

## クラスに情報をひたすら登録していく

この時点で `Unko1` はサイズ 0 の構造体としてしか認識されてないから `void *` だった時からコードはほとんど変化していない。

ということで `Unko1::Unko1` を実行するコードを探せば、その直前にメモリアロケーターがいるはずである。

## Ghidra でも復元できないコードがある

ただなんとなく第 2 引数の `param_1` とメンバ変数の `unknown4` は GUID 構造体くせえなぁと俺の第六感が囁くのである。

```c++
Unko1 * __thiscall Unko1::Unko1(Unko1 *this, const GUID *guid, undefined4 param_2, undefined4 param_3)

{
...
  this->guid = *guid;
...
}
```

みたいに構造体の代入やってんじゃねえのという、だがしかし Ghidra は構造体の代入式を正しく復元できないので

```c++
  (this->guid).Data1 = param_1->Data1;
  uVar1 = param_1->Data3;
  (this->guid).Data2 = param_1->Data2;
  (this->guid).Data3 = uVar1;
  *(undefined4 *)(this->guid).Data4 = *(undefined4 *)param_1->Data4;
  *(undefined4 *)((this->guid).Data4 + 4) = *(undefined4 *)(param_1->Data4 + 4);
```

と可読性が逆に悪化してしまうのだ、まぁコンパイラは代入をメモリブロック転送命令で片付けるからしかたないね。

```asm
        02002e3f 8b f8           MOV        EDI,EAX
        02002e41 a5              MOVSD      ES:EDI,ESI
        02002e42 a5              MOVSD      ES:EDI,ESI
        02002e43 50              PUSH       EAX
        02002e44 a5              MOVSD      ES:EDI,ESI
        02002e45 53              PUSH       EBX
        02002e46 52              PUSH       EDX
        02002e47 a5              MOVSD      ES:EDI,ESI
```

`memcpy` なんかもコンパイラが最適化にインライン展開するので、構造体なんかの型を指定すると余計に可読性が落ちるケースが多い、なのでコメントでここは代入だよって書き残すしかないね。
それに `GUID` 構造体という確証もまだ無いのでそのままにしておくか。

最後に仮想関数テーブルの名前も `PTR_FUN_02001384` から `VFTBL_Unko1` とでも変えておこう。

## 閑話 メモリ開放前に機微情報はゼロクリアしろ

開放されたメモリからパスワードなんかの重要情報を読み取れたりするからね。
最適化によってメモリ開放される前に `memset`でゼロ埋めしてもコンパイラはそれを消すこともあるから消し方も重要。
C11 で導入された `memset_s` で消そう、つーか C23 では `memset_explict` が追加されて今はこっちが推奨なんだっけ。
これは C11 が `memset_s` の実装を任意とするなんてやってしまったせい。

まだ界隈のジジイどもが元気だったのでバイク小屋論争で揉めたんですわ、俺の覚えてるだけで似たようなものがこんだけある。

* `SecureZeroMemory` … Windows
* `memzero_explicit` … Linux
* `explicit_bzero` … O
* `explicit_memset` … N

うん `volatile` 指定した関数ポインタ経由で `memset` 呼ぶのが一番移植性が高いわクソが。

## 閑話休題

他は COM 関連だと思われるので俺の現時点での知識じゃ何やってるのかさっぱり、ただ `unknown5` の型は `HANDLE` らしいというのは判った。
`0xffffffff` は無効なハンドルを指す `INVALID_HANDLE` マクロの値だもんね。

コンストラクタとデストラクタ以外のメンバ関数も第 1 引数を `Unko1 *` にして可読性を高めていくのだけど、この際にちょっと注意が必要。

## C と C++ では呼び出し規約が異なる

通常 Visual C/C++ においてメンバ関数の呼び出し規約はコンストラクタの話でもちょっと触れたけど `__thiscall` である。
これは第 1 引数の `this` をスタックに積まずレジスタ (x86 の場合は ECX) で経由で渡す、これによってスタックのプッシュポップのコストを削減する。
C++ のメンバ関数は C のフリー関数より常に 1 個引数が多いわけで、このプッシュポップのコストも塵も積もれば山となり性能面でのデメリットも無視できなかったんだろう。

しかし COM インタフェースは C からも呼び出す必要があるので C ABI である必要がある、よって `__thiscall` は使えないのだ。
C 側はレジスタに `this` がレジスタ上にあるなんて知らないから仕方ないですな。

そんで伝統的な C ABI では通常は引数は右から左にスタックに積んで(評価順は未定義)スタックの掃除は呼び出し元が行うことになっている、これを Microsoft は `__cdecl` と呼んでいる。
これは `printf` ライクな可変長引数の実装に必要なのだが、アセンブラにした時の可読性とバイナリサイズの最適化と性能面で不利なのだ。
それに可変長引数は型安全が死ぬからな、`va_list` とか悪夢としか言いようがない。

## 閑話 モダン()な言語は `__cdecl` の悪夢は繰り返さない

Java や Pascal のように可変長引数が無い言語は可読性のためにスタックは左から右に積み(評価順も左から右)、コードサイズの最適化と性能の為にスタックの掃除は呼ばれた関数が実行する。
まぁ理想と現実は違うので Java も Delphi も可変長引数もどきを実装する羽目になるのだが、これらは配列あるいはオブジェクトを使って実装してるので ABI はそのままである。
Java5 で `java.io.PrintStream#printf` が生えた時はマジ腹抱えて笑った、みんな C 好きなんすね～ゴスリングの負け。

それにしてもスタックに積む順番ごときで可読性が～って凄い時代なのだが、プログラマってのは 8086 アセンブラの Intel 表記と AT&T 表記どちらが優れているかで延々レスバできる悲しい生き物である。

## 閑話休題 `__stdcall` の誕生

当時を知らない世代には信じられないだろうが、当時は「本物のプログラマはPascalを使わない」どころか Visual C++ の前身の Microsoft C/C++ は Delphi の前身 Turbo Pascal に遅れをとってたのだ。

なので Windows NT 3.1 で 32bit 化するタイミングで伝統的な C ABI を捨て、新たに `__stdcall` を採用することにした。
右から左にスタックに積むのは従来通りだけど、スタックの掃除は Pascal 同様に呼ばれた関数が行うようにして Pascal と同等のバイナリサイズと性能を実現するものだった。
`printf` のような可変長引数がある関数についてのみ `__cdecl` が使われる。

ちなみに `__stdcall` と一緒に `__fastcall` という引数のうち右ふたつをレジスタ渡しにする呼び出し規約も追加されている、それに対して Boland はそれならうちはみっつにしてデフォルトにする！だとか Watcom はうちなんかよっつだぜ！子供のような争いが繰り広げられるのだがいい加減にしろ。
ブレードランナーの屋台のおっちゃんの「ふたつで十分ですよ、わかって下さいよ」はこのレジスタ数競争を諫めていた…？

それでもなお Windows プログラミングするなら Visual Studio より Delphi という風潮はヘルスバーグが Borland をリストラ(正しい用法)され Microsoft に拾われた後もしばらく続いた。
これは単純に RAD としての出来の良さがダンチだったから。ポトペタで猿でも画面作れるしコンパイルも速いし VCL は静的リンクだからランタイムも不要で DLL 地獄とは無縁だったし。
でも Borland が突然自ら命を絶ってしてしまったのでそんな時代もおしまい、国を失ったディアスポラは無謀にも Java に流れるのだけど Java の開発環境も Delphi で書かれてた Visual Cafe と初期の JBuilder 以外はすべてゴミでやんした。
その中でも Interstage Apworks だけは絶対に許さない。

というわけで COM インタフェースの ABI は `__thiscall` でも `__cdecl` でもなく `__stdcall` になる。
よってクラスメンバ関数だからと `__thiscall` に脳死で変更すると解析結果がぶっ壊れてしまう。
