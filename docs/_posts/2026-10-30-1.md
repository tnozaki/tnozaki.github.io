## Ghidra の呼出規約の復元は信用するな

まず最初に疑ったのは前回もでてきた呼出規約である。

* `__stdcall` であれば `this` はスタック渡し
* `__thiscall` であれば `this` はレジスタ渡し

よって `__stdcall` の場合スタック渡しされた `this` を ECX レジスタにコピーするのだけど、そのコードが正しく解釈できてない可能性がある。

じゃあいアセンブラ読もうか、Ghidra の逆アセンブルコードって Intel 記法ベースの上に婉曲表現で理解しづらいなこれ。

```asm
                             **************************************************************
                             *                          FUNCTION                          *
                             **************************************************************
                               HRESULT __stdcall FUN_0200370a(Unko1 * this, long param_
                               assume FS_OFFSET = 0xffdff000
             HRESULT           EAX:4          <RETURN>
             Unko1 *           Stack[0x4]:4   this                                    XREF[3]:     02003711(R), 
...
                             Unko1::FUN_0200370a                             XREF[1]:     020013a0(*)  
…
        0200370c 55              PUSH       EBP
        0200370d 8b ec           MOV        EBP,ESP
…
        02003711 8b 4d 08        MOV        ECX,dword ptr [EBP + this]
…
```

* `this` は `Stack[0x4]:4` つまり スタックフレーム + 4 の位置にある 4byte データ
* `EAX` レジスタのリターンアドレス 4byte が退避されてるからスタックフレームは `[EBP + 4]` の位置
* よって `[EBP + this]` は `[EBP + 8]` の意味、通常ここには第 1 引数が積まれる
* `MOVE ECX, [EBP + 8]` つまりスタックに積まれた第 1 引数 `this` を `ECX` レジスタにコピーしている

ということで推測は正しかった。

そんで `SimpleFactory` は `IUnknown` のメンバ関数で `__thiscall` ちゅうことかと思ったのだが、開けてびっくり `__fastcall` になっとるんよ。

```c++
void __fastcall
FUN_02002e86(undefined4 param_1,int param_2,int param_3,int param_4,GUID *param_5,
            undefined4 *param_6)
```

`__thiscall` が誤判定されたのかと一瞬思ったが、そもそも明示的に指定しなければ `__fastcall` にはなるはずがないので Ghidra が ECX に `this` を置いたみて `__fastcall` と早とちりしたっぽい。

そんで戻り値があるはずなのに `void` になっとるのもおかしいわな。

これらの問題を修正するに `SimpleFactory` のプロトタイプは `__stdcall` であり

```c++
HRESULT SimpleFactory(undefine4, undefined4, IID*, void**);
```

が正しいのかなと。

x86_64 なら最初の引数 4 個は必ずレジスタ渡しになるから呼出し規約なんて有名無実化してるので誤判定なぞ起きようが無い。
幸運なことに今回は 64bit 版の CtDPROXY.DLL もあるのだから、そっち解析すれば正しい答えが出るよね。

x86_64 でも基本 x86 と同じ手順だからそこの解説は省略させていただく、ただしコンパイラの進化によって以下の違いがあることを知らないと大変だと思われる。

* 最適化ががっつり効いてて `GUID` 定数が全部インライン展開され .text セクションにそもそも存在しないから、GUID の先頭 64bit でメモリ検索しないと探せない
* コンストラクタもデストラクタもすべてインライン展開されている
* もはや inline キーワードは有名無実化しすきあらば性能の為にインライン展開される
* ありとあらゆる最適化により鼻から悪魔が飛び出す
* AddRef/Release での参照カウントの増減は `InterlockedIncrement/InterlockedDecrement` を使わず `LOCK/UNLOCK` によるクリティカルセクションで実装されている

今の子は大変だね(憐憫)、そんで見つかったプロトタイプがこちら。

```c++
HRESULT SimpleFactory(undefined8, IID*, void**);
```

あー引数 3 つで第 1 引数は 64bit でそれが 32bit + 32bit に解釈されて引数 4 つに化けてんだわ、これについてはなぜそうなるかは後で説明する。

32bit 非 thunking 版の方も見てみるとこっちも `__fastcall` に誤判定されてたけどそこ修正してやると

```c++
HRESULT SimpleFactory(undefined4, IID *,void **);
```
とやはり引数 3 つだったわ、正解出たね。

前回軽く触れた thinking のサンプルやねこれ、コードを脳内で書き直すと以下のようになる。

しかし LLP64 ってのは 32bit でも 64bit でも `long` は 32bit だからコードの移行が楽なんて言われてるけど、Thunking が必要なケースになると非常にめんどくせえなこれ。

ところでなぜ Ghidra の疑似 C ソースを修正せずにず脳内で処理したか、それは Ghidra がバグっとるから。

## Ghidra はコンパイラがインジェクションしたコードの解釈があまり得意でない

そして謎のマジックナンバー `0x2003582` `0x2003594` なんてのまで現れた。

```c++
  uStack_1c = 0x2003582;
  uStack_44 = 0x2003594;
```
これは大きなサイズのスタック要求に対して Visual C/C++ は `alloca_probe` を呼び出しスタックオーバーフローを検知しようとする。

```asm
        0200357d e8 ae a7        CALL       __alloca_probe                                   undefined __alloca_probe(void)
                 00 00
        02003582 8b c4           MOV        EAX,ESP
…
        0200358f e8 9c a7        CALL       __alloca_probe                                   undefined __alloca_probe(void)
                 00 00
        02003594 83 66 04 00     AND        dword ptr [ESI + Stack[-0x3c]],0x0
```

マジックナンバーは `__alloca_probe` 呼出の次の命令のアドレスですな、つまりこれも Ghidra のバグである。

大きなスタックサイズ要求というのは `DeviceIoControl` の引数となるローカル変数宣言 `local_40` の 32byte(0x20) と `local_58` 16byte(0x10) である、全然小さいやんけ。

Ghidraは構造体までは復元できないので

* 入力データ

```c++

  undefined4 local_34;
  undefined4 local_30;
  undefined4 local_2c;
  undefined4 local_28;
  undefined4 local_24;
```

* 出力データ

```c++
  undefined1 local_58 [8];
  undefined4 local_50;
  undefined4 local_4c;
```

のようにバラバラのローカル変数となってしまうので、以下の構造体を Ghidra に登録する。


* `local_40` の型を `FUN_02003566_In` 名前を `inData` に
* `local_58` の型を `FUN_02003566_Out` 名前を `outData` に

よっしゃ謎のマジックナンバー入れてる変数が消えた。

ちなみに `DeviceIoControl` は Unix でいうところの `ioctl` で In/Out はドライバ固有なので構造体のメンバがそれぞれ何を意味するのかはデータシートでも手元に無いと判らん。
`inData` の先頭 8byte はおそらく ABI バージョンだとは想像つくが他はさっぱり、俺はドライバ屋でもハード屋でもないし。
kX Project 2 の Emu10k オープンソースドライバを読めばわかるかもしれないが、あれどうやって調べたんだろうな。

そして戻り値を返すはずなのに返さない問題、こいつは過去回でも解説したのだが Visual C/C++ の /GS オプションすなわち Guard Stack によるスタック破壊からのリターンアドレス書換攻撃を防ぐためのインジェクションコードが悪さをしてるせい。

* リターンアドレスの手前、スタックの底に置かれるカナリア、ローカル変数 canary
* 乱数の入ってるグローバル変数 `__security_cookie`
* カナリア変数が破壊されてないかをチェックする CRT の関数 `__security_check_cookie`
* スタックベースポインタを表す `stack0xfffffffc` つまり `EBP`

こいつらは全部インジェクションコードなので Ghidra が消し込まないとならないのだがそこが盛大にバグっていることで発生する。
